# 自作カレンダーアプリ（Phase 1）

Google カレンダーの予定を読み取り専用で取得し、予定の種類ごとに自動で色分けして表示する PWA です。
入力・編集機能は持ちません（予定の追加・変更は Google 公式アプリで行います）。

要件定義書（`docs/calendar-requirements.pdf`）の **Phase 1：表示設計の検証** の範囲を実装しています。

---

## 1. まず見た目だけ確認する（Google 連携なし）

ローカルサーバーを立ち上げて、ダミーデータで表示を確認できます。

```bash
python3 -m http.server 8765 --directory "my-calendar"
```

ブラウザで <http://localhost:8765/index.html?demo=1> を開きます。
（`?demo=1` を付けた時だけダミーデータで動きます。認証も通信も行いません。）

スマホの画面幅で確認したいときは、ブラウザの開発者ツールでモバイル表示に切り替えてください。

## 2. 自分の Google カレンダーに接続する

### 2-1. Google Cloud Console で OAuth クライアントを作る

1. <https://console.cloud.google.com/> を開く
2. 上部のプロジェクト選択 →「新しいプロジェクト」→ 名前は任意（例：`my-calendar`）
3. 左メニュー「API とサービス」→「ライブラリ」→ **Google Calendar API** を検索して **有効にする**
4. 「API とサービス」→「OAuth 同意画面」
   - User Type: **外部**
   - アプリ名・サポートメール・デベロッパー連絡先を入力
   - スコープ: **`.../auth/calendar.readonly`** と **`.../auth/calendar.events`** の2つを追加
     （前者は予定の閲覧、後者はアプリから予定を追加するために必要）
   - テストユーザー: **カレンダーを見たいアカウントのアドレスを追加**
     - **複数登録できます。** 実際に使うアカウントと、予備のアカウントの両方を入れておいて構いません
     - ここに入っていないアカウントでログインすると「アクセスをブロックしました」になります
   - 公開ステータスは「テスト」のままでよい（CON-01：ログイン時に「確認されていません」の警告が出るが、本人利用のため許容）
5. 「API とサービス」→「認証情報」→「認証情報を作成」→ **OAuth クライアント ID**
   - アプリケーションの種類: **ウェブ アプリケーション**
   - **承認済みの JavaScript 生成元** に、アプリを開く URL を登録する
     - ローカル確認用: `http://localhost:8765`
     - 公開後: `https://<ユーザー名>.github.io` など、実際に開くオリジン
   - リダイレクト URI は不要
6. 作成後に表示される **クライアント ID**（`……apps.googleusercontent.com`）を控える

> ⚠️ **クライアントシークレットは使いません。** このアプリはブラウザ内で完結するため、シークレットを
> ファイルに書いたり誰かに渡したりしないでください。

### 補足：複数の Google アカウントを使う場合

- **Cloud プロジェクトを作るアカウント**と、**カレンダーを見るアカウント**は別で構いません。
  プロジェクトはどちらか使いやすい方で1つ作り、見たいアカウントを 4. のテストユーザーに追加します。
- **会社・学校の Google Workspace アカウント**の場合、管理者が外部アプリの利用を制限していると
  ログイン時にブロックされることがあります。その場合はそのアカウントで Cloud プロジェクトを作り、
  User Type を **内部** にすると通ることがあります（管理者設定によります）。
- **アプリは一度に1アカウント**です（PRE-01）。別アカウントに切り替えるときは設定画面からログアウトします。
- **2つのアカウントの予定を1画面で見たい場合**は、アプリではなく Google カレンダー側で解決します。
  見られる側のカレンダーを、使う側のアカウントに**共有**しておけば、取り込み対象カレンダーの一覧
  （FR-08）に現れ、オン/オフで表示を切り替えられます。

### 2-2. アプリにクライアント ID を渡す

どちらかの方法で設定します。

- **方法A（おすすめ・スマホでも可）**: アプリを開くと入力欄が出るので、クライアント ID を貼り付けて
  「Google でログイン」を押す。端末内（localStorage）にのみ保存されます。
- **方法B**: `js/config.js` の `CLIENT_ID` に直接書く。

### 2-3. ログイン

<http://localhost:8765/index.html> を開き、「Google でログイン」→ Google の画面で自分のアカウントを選択。
「このアプリは確認されていません」と出たら「詳細」→「（アプリ名）に移動」で進みます（CON-01）。

要求される権限は **カレンダーの閲覧のみ**（`calendar.readonly`）です。

## 3. 色ルールを自分の予定に合わせる

`js/color-rules.json` を編集します（Phase 1 は設定画面ではなくファイル直書き＝FR-19c）。

```json
{
  "categories": [
    { "id": "work", "label": "仕事", "color": "#1a73e8" }
  ],
  "rules": [
    { "keyword": "会議", "category": "work" }
  ]
}
```

- `rules` は **上から順に評価され、最初に一致したものが採用されます**（FR-14 先勝ち）。
  細かいルールを上に、広いルールを下に置いてください。
- 判定は **タイトルの部分一致**（FR-12）。比較前に全角/半角・大文字/小文字を揃えます（FR-13）。
- どれにも一致しない予定は **グレー**（FR-15）。
- 2つ以上に一致した予定は、先勝ちの色に **●印** が付きます（FR-16）。
- **`【 】` で囲んだキーワードは「本人が付けた印」として扱い、●印を出しません。**
  追加フォームで種類を選ぶとこの印が予定名の先頭に付くため、印が付いていれば判定は確定とみなします。
- **先頭の `【 】` は画面には表示しません。**色が種類を伝えるので文字としては不要で、
  1マスの狭い幅を印で埋めないためです。Google カレンダー側のタイトルには残ります
  （印がないと次に開いたときに色が決まらないため）。
- 色数に上限は設けていません（FR-17 からの変更）。ただし8色を超えると起動時に警告が出ます。
  凡例を見ずに見分けられる限界がそのあたりだからです。

`categories` を増やしたり名前を変えたときは、**`【名前】` のルールも合わせて直す**こと。
追加フォームの種類チップは `categories` から作られ、選ぶと `【label】` が予定名に付く仕組みのため。

**初期値は仮置きです。** 実際の予定タイトルを一度棚卸しして書き換えてください（OPEN-02 / OPEN-03）。

## 5. 操作

| 操作 | 動作 |
| --- | --- |
| 日付をタップ | その日の予定を下部に表示 |
| 左右スワイプ / `‹` `›` | 前月・翌月（FR-27） |
| 下に引っ張る | 手動で最新データを取得（FR-04） |
| 予定をタップ | Google カレンダーの該当予定を開く（FR-26） |
| メモをタップ | メモの全文を表示（FR-24） |
| 右下の `＋` | 予定を追加する（下記）|
| 詳細の予定を左スワイプ | 削除ボタンが出る。押すと確認のうえ削除（Google のゴミ箱に入る） |
| 右上 `☰` | 取り込むカレンダーのオン/オフ、色ルールの凡例、ログアウト |

アプリを開いたとき・他アプリから戻ったときに自動で最新データを取得します（FR-03）。
定期ポーリングやプッシュ通知は行いません（FR-05）。

### 予定を追加するときの入力

入力の手数を減らすため、次のようにしている。

- **種類（色）**：ボタンで選ぶ（必須）。選ぶと予定名の先頭に `【仕事】` のような印が付き、その色になる。
  既定では何も選ばれていない。取り違えて別の色で登録されるより、1回選ばせる方を採った
- **日付**：入力欄を置いていない。月表示で選んでいる日に入る。見出しに「8月3日(月) に追加」と出す
- **開始 / 終了**：どちらも時刻の入力欄。開始は次のキリのよい時刻、終了はその1時間後が初期値。
  開始を動かすと、それまでの所要時間を保ったまま終了もずれる
- **メモ**：欄を置いていない。書きたいときは予定をタップして Google 公式アプリで開く。
  なお**詳細エリアでの表示はそのまま**なので、Google 側で書いたメモは今までどおり読める
- **追加先のカレンダー**：欄を置いていない。書き込めるメインのカレンダーに入る

## 8. Phase 1 の完了判定

**「Google 公式アプリより本アプリのほうが予定を把握しやすい」と自分で判断できること。**

1週間以上、実際の予定で使ってから判断します。判断できない場合は Phase 2 へ進まず、
バー本数・色数・分割比率を見直します（要件定義書 9章）。

検証中に確認したい未解決事項：

- OPEN-01 場所を詳細に出さなくて困らないか
- OPEN-04 終日予定のバー表現（現状は角を立てた四角いバーで暫定的に区別）
- OPEN-05 ダークモードの要否

### 要件定義書からの変更（Phase 1 の実運用で確定）

**FR-23（詳細表示）**：「開始〜終了時刻」と「メモ」のみと定めていたが、メモのない予定が
時刻だけの行になり内容を判別できなかったため、**予定タイトルを表示し、それを主役にする**方針に変更。
時刻は補助情報として小さく表示する。`SHOW_TITLE_IN_DETAIL` を `false` にすれば元の仕様に戻せる。

**FR-22（月表示のバーに文字を載せない）**：月表示だけである程度中身を把握したいという判断から、
**バーに予定名を載せる**方針に変更。あわせて上下の分割比率を月表示側へ寄せた（64:36）。
`SHOW_TITLE_IN_MONTH` を `false` にすれば、文字なしの細い色バー（元の仕様）に戻る。

この変更により「色の面だけで全体像を把握する」という当初の狙いは弱まる。1週間の運用で
月表示がうるさく感じるようなら、`false` に戻して比較すること。

月表示の行数は固定6週ではなく、**その月が占める週数（4〜6週）だけ描く**。
5週で収まる月は1マスが2割ほど高くなり、予定名が読みやすくなる。

**3.2「予定の作成・編集・削除は作らない」／ PRE-04・NFR-06「読み取り専用」**：
アプリからも予定を入れたいという判断から、**追加**（右下の `＋`）と**削除**（詳細を左スワイプ）を実装した。
**編集は引き続き作らない**。直したいときは予定をタップして Google 公式アプリで開く。

削除は誤操作を避けるため、スワイプ → 削除ボタン → 確認ダイアログの3段階にしている。
Google 側ではゴミ箱に入るため、消しすぎても Google カレンダーから復元できる。

これに伴い認証スコープに `calendar.events`（予定の書き込み）を追加している。
**既にログイン済みの端末は、権限が増えたぶんログインし直す必要がある**
（設定 → ログアウト → 再ログイン）。Google Cloud Console の OAuth 同意画面にも
このスコープを追加しておくこと。
